Development

Rust WorkspaceとVueを、同じリポジトリで。

Rust側はCargo Workspace、フロントはViteを利用します。開発時は一時Unixソケットを指定すると、root権限なしでServer–Agent通信を確認できます。

リポジトリ構成

apps/
├── agent/          # Rust / Linux Agent
├── server/         # Rust / Axum Server
└── web/            # Vue + TypeScript
crates/
└── protocol/       # 共有Serialize型
packaging/
├── config/
├── scripts/
└── systemd/
docs/               # このHTMLドキュメント
scripts/
└── package-release.sh

Rustプロセスを起動

最初のターミナルでAgentを起動します。

DECKOX_AGENT_SOCKET=/tmp/deckox-agent.sock \
cargo run --package deckox-agent

開発用パスワードのハッシュを作り、次のターミナルでServerを起動します。Vueの本番ビルドを配信する場合はDECKOX_WEB_DIRを指定します。

printf '%s' '開発用パスワード' \
  | cargo run --quiet --package deckox-server -- hash-password \
  > /tmp/deckox-admin-password.hash
DECKOX_AGENT_SOCKET=/tmp/deckox-agent.sock \
DECKOX_WEB_DIR="$PWD/apps/web/dist" \
DECKOX_ADMIN_PASSWORD_HASH_FILE=/tmp/deckox-admin-password.hash \
cargo run --package deckox-server

Vue開発サーバー

cd apps/web
npm install
npm run dev

Viteはhttp://localhost:5173で起動し、/apiと/healthzをhttp://127.0.0.1:8080へプロキシします。

本番ビルド:

cd apps/web
npm ci
npm run build

CLIサブコマンド

deckox-serverは先頭引数でサブコマンドを切り替えます。reset-password・disable-totpはアカウントファイルへ直接読み書きするため、実行後はdeckox-serverを再起動します。

コマンド動作
hash-password標準入力のパスワードをArgon2idハッシュへ変換して標準出力へ表示。DECKOX_ADMIN_PASSWORD_HASHの初期値作成に使用
reset-password標準入力の新しいパスワードでDECKOX_ADMIN_PASSWORD_HASH_FILEのパスワードだけを更新。TOTP設定は変更しない。監査ログへpassword_reset_cliを記録
disable-totp対話確認後、アカウントのTOTP設定とリカバリーコードを削除。監査ログへtotp_disabled_cliを記録
access-urlAgentに/v1/systemを問い合わせ、LAN上のIPv4アドレスとDECKOX_LISTEN_ADDRのポートからhttp://IP:port形式のアクセスURLを表示。Agentに接続できない場合もポート番号だけは表示する

reset-password・disable-totpは永続化されたアカウントファイルが前提のため、DECKOX_ADMIN_PASSWORD_HASHだけが設定されている場合はエラーで終了します。

printf '%s' '新しいパスワード' | sudo -u deckox deckox-server reset-password
sudo -u deckox deckox-server disable-totp
sudo -u deckox deckox-server access-url

診断APIのデータ境界

GET /api/v1/diagnosticsは画面表示用のJSON、GET /api/v1/diagnostics/reportは同じ内容のダウンロード応答です。どちらも管理者認証が必要です。

レスポンスはgenerated_at_ms、Serverのversion・status、Agentのconnected・version・error code、公開可能なhost情報、2つのDeckox systemdユニット状態、runtime configの真偽値と件数に固定されています。Agent APIに接続できない場合もHTTPエラーにはせず、Agent由来のまとまりをnullにした部分診断を返します。

診断機能へ項目を追加するときは、生の設定・環境変数・ログ・認証情報を転送せず、共有Protocolへ明示した安全な値だけを追加します。パスワード、ハッシュ、セッション、Cookie、boot IDは追加禁止です。

更新確認API

GET /api/v1/updateは管理者認証が必要です。固定リポジトリの最新Releaseタグだけを読み、現在のCARGO_PKG_VERSIONとSemVer比較します。成功・失敗は15分キャッシュされます。

GitHubへの要求はHTTPS、5秒、リダイレクトなし、最大64 KiBです。取得不能・不正JSON・不正タグはいずれもHTTP 200のunavailableへ正規化し、外部の本文やURLはブラウザへ渡しません。

更新実行API

POST /api/v1/system/updateは管理者パスワードの再確認が必要で、Agent設定system.allow_updateがtrueでなければ拒否されます。Serverは受理前に更新確認結果を再評価し、update_availableでなければ拒否します。クライアントはターゲットバージョンを指定できず、Serverが確認済みのタグだけを使用します。

Serverはhttps://raw.githubusercontent.com/<repo>/<tag>/packaging/scripts/install.sh(タグはvMAJOR.MINOR.PATCH形式のみ許可)を最大256 KiBまで取得し、内容を検証してからAgentのUnixソケットAPIへ渡します。Agentは同じタグ形式とスクリプト長を再検証したうえで固定パス(/run/deckox/update.sh、パーミッション0600)へ書き込み、systemd-run --collect --no-block --unit=deckox-updateで独立したtransientユニットとして実行します。deckox-agent.service自身のcgroup内で実行すると、インストーラーが行うsystemctl restart deckox-agentで処理の途中に強制終了されるため、この分離が必須です。

Agentは自らGitHubやその他の外部ネットワークへ接続しません。実行内容は既存のinstall.shと同じバックアップ・起動確認・失敗時ロールバックの手順です。

systemd操作の許可リスト

サービス状態の読み取りは常に可能ですが、起動・停止・再起動・有効化・無効化とjournalログ閲覧は、Agent設定へ完全一致で登録したサービスだけが対象です。

socket = "/run/deckox/agent.sock"

[system]
allow_reboot = false
allow_update = false

[software]
allowed = []

[services]
allowed = [
  "nginx.service",
  "postgresql.service",
]

deckox-agent.serviceとdeckox-server.serviceは登録しても起動時に拒否されます。

journalログは最大500行までで、priorityはall・error・warning・infoだけを指定できます。任意のjournalctl引数、Webコンソールは提供しません。表示中のログはJSONファイルとして保存できます。

許可リストはPOST /api/v1/services/{id}/allow・POST /api/v1/services/{id}/disallowから追加・削除でき、管理画面のサービス一覧からも操作できます。追加前にsystemctlでサービスの存在を確認し、存在しないIDは拒否します。deckox-agent.serviceとdeckox-server.serviceはどちらのエンドポイントでも対象外です。書き込みはagent.tomlの[services]セクションのみを置換する形で行い、コメントを含む他のセクションは保持します([services]が[software]より後の、ファイル末尾のテーブルであることを前提とした実装です)。設定はプロセス内の許可リストとファイルの両方へ即座に反映され、Agentの再起動は不要です。

system.allow_rebootは初期値falseです。trueにした場合だけ、パスワード再確認後のホスト再起動を受け付けます。system.allow_updateも初期値falseで、trueにした場合だけ管理画面からの更新実行を受け付けます。

サービス一覧の各項目には、判定によるタグが付与されます。ユニットファイルのFragmentPathが/usr/lib/systemd/system/または/lib/systemd/system/配下にある場合は「標準」(OS・パッケージ提供)、IDがdeckox-agent.service・deckox-server.serviceと一致する場合は「Deckox」タグになります。どちらにも該当しないサービス(/etc/systemd/system/などローカルに配置されたユニット)はタグなしです。

これとは別に、ユニット名の基本部分(@instanceと.serviceを除いた部分。例: postgresql@14-main.serviceならpostgresql)を既知の主要ソフトウェアの一覧と突き合わせ、一致すれば製品名タグ(例: docker.service→「Docker」)を付与します。standard_systemとは独立した判定なので、両方のタグが付くこともあります。ストレージのマウント一覧にも同様に、マウントポイントが/・/boot・/boot/efi・/home・/var・/tmpのいずれかと完全一致する場合だけ「標準」タグを付与します(サブディレクトリやDockerのoverlayマウントなどは対象外)。

ソフトウェア管理の許可リスト

固定のカタログは持ちません。apps/agent/src/software.rsのPackageManagerenum(Apt・Dnf・Pacman・Zypper)が、Agent起動時にapt-get --version・dnf --version・pacman --version・zypper --versionを順に試して(Command::outputはバイナリが無ければErrを返すだけで、シェルは経由しない)ホストのパッケージマネージャーを1回だけ判定します。

POST /v1/software/{name}/allowは、管理者が入力した任意のパッケージ名を、そのホストに既に設定済みのリポジトリだけを対象に実在確認してから許可リストへ追加します。apt側はapt-cache policy <pkg>のCandidate:行、dnf側はdnf --quiet list <pkg>の出力(Installed Packages/Available Packagesセクション)、pacman側はpacman -Si <pkg>のVersion行、zypper側はzypper info <pkg>のVersion行を読み、いずれも見つからなければ404で拒否します。新しいリポジトリやGPG鍵を追加することはありません。

一覧取得(GET /v1/software)は許可リスト内パッケージだけを対象に、同じ実在確認ロジックでインストール状態・バージョンを読みます。いずれのバックエンドも読み取り専用でインデックス更新は行いません(診断画面の更新可能パッケージ数と同じ方針)。dnf・zypperは1回のコマンド実行でインストール済み・入手可能バージョンの両方を読める設計(PackageManager::status())にしており、一覧の各行ごとに同じコマンドを2回実行することはありません。zypperのインストール済みバージョンはzypper infoではなくrpm -qから直接読みます(zypperバージョンによってinfoのVersion欄がインストール済み/候補どちらを指すか曖昧なため)。アップグレード可否も同じ理由でzypper list-updatesの表から判定します。

インストール・更新は実行直前に一度だけインデックスを更新してから(apt: apt-get update、dnf: dnf makecache --refresh、zypper: zypper refresh)、apt-get install -y/dnf install -y/zypper installを実行します。削除はapt-get remove -y/dnf remove -y/zypper removeで、aptは設定・データを残しますが、dnf・zypperには同等の使い分けがなく設定ファイルも削除される場合があります。更新は対象がインストール済みでない場合409 conflictで拒否します。

pacmanだけは他と異なり、インデックス更新(-Sy)とパッケージ適用を分離しません。-Sy単独の実行はpacmanコミュニティが明確に非推奨とする「partial upgrade」状態(依存関係の不整合)を招くリスクがあるため、インストール・更新のどちらもpacman -Syu --noconfirm <pkg>(フルシステムアップグレード込み)を1回実行します。結果として、pacmanホストでの「1パッケージのインストール/更新」はホスト全体のパッケージも同時に最新化するという、apt/dnf/zypperより副作用の大きい挙動になります。削除はpacman -R --noconfirm <pkg>です。

許可リストの追加・削除(POST /v1/software/{name}/allow・/disallow)はサービスの許可リストと同様、管理者セッションだけで実行できます。一方インストール・削除・更新は、ホスト再起動・自己更新と同じconfirm_password_or_respond()(Server側、main.rs)でパスワード再確認を必須にしています。ホストの実際の状態を変える操作だからです。

Alpine LinuxはsystemdではなくOpenRCのため、ソフトウェア管理に限らずDeckoxのサービス管理そのものが対象外です。

サービスのスケジュール実行

許可リスト内のサービスに限り、起動・停止・再起動を曜日(月-日、複数選択可)と時刻(ホストのローカル時刻、分単位)を指定して自動実行できます。管理画面のサービス一覧から登録・削除・有効/無効の切り替えができ、SSHでの設定は不要です。

Agentは20秒ごとに現在の曜日・時刻を確認し、一致するスケジュールをServiceManager::control(手動操作と同じ経路)で実行します。同じ分に複数回確認しても実行は一度だけです。Agentが再起動した場合、直前の実行記録は保持されないため、再起動とちょうど重なった分は再実行される可能性があります(許容している既知の制限です)。

登録内容は/var/lib/deckox/schedules.jsonにJSONとして永続化されます(TOMLの配列テーブルを手書きで編集するconfig::write_allowed_servicesのような仕組みは、この用途には見合わないため採用していません)。パスはDECKOX_SCHEDULES_FILE環境変数で上書きできます。

実行結果(成功、または失敗理由)と前回実行日時はスケジュールごとに記録され、管理画面の一覧に表示されます。定期実行そのものはAgent内で完結するため、Serverの監査ログには残りません(スケジュールの登録・削除・有効化・無効化という管理操作は監査ログに記録されます)。deckox-agent.service・deckox-server.serviceはスケジュール登録の対象外です。

Docker Compose

docker compose up --build

ComposeはServer–Agent通信とUIを確認するための開発構成です。http://127.0.0.1:8080/を開き、固定の開発用パスワードdeckoxでログインします。パスワードハッシュを環境変数で渡すため、設定画面からのパスワード変更は利用できません。

制限: コンテナ内のAgentはLinuxホストのsystemdを管理できません。本番のLinux管理用途ではsystemdサービスとして導入します。
