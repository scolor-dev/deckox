Version 0.6.8

Installation

1つのコマンドから、2つのサービスを導入。

インストーラーはGitHub ReleaseからCPUに合うアーカイブを取得し、SHA-256を検証してServer・Agent・Vue・systemdユニットを配置します。

リリースから導入まで

対応CPUアーキテクチャ

uname -mRust targetRelease
x86_64 / amd64x86_64-unknown-linux-muslビルド定義済み
aarch64 / arm64aarch64-unknown-linux-muslビルド定義済み

GitHub Actionsはx86-64とARM64を別Runnerでビルドします。両方が成功した場合にReleaseを作成します。

Releaseの作成

v*タグのpushでRelease Workflowが起動します。

git tag v0.6.8
git push origin main
git push origin v0.6.8
実行条件: インストールコマンドを利用するには、対象タグのGitHub Releaseと4つの配布ファイルが公開済みである必要があります。

Linuxへインストール

curl -fsSL \
  https://raw.githubusercontent.com/scolor-dev/deckox/main/packaging/scripts/install.sh \
  | sudo sh

初回インストールで対話端末が使える場合、待受アドレス(ローカルのみ/LAN内のこのホストのアドレス)、ホスト再起動の許可、更新適用の許可を尋ねます(curl | sudo shの形でも、制御端末があれば入力できます)。無人インストールや対話端末がない場合は質問せず、従来どおりの既定値(ローカルのみ、両許可とも無効)のまま導入します。既定値以外を無人で指定したい場合はDECKOX_LISTEN_ADDR・DECKOX_ALLOW_REBOOT・DECKOX_ALLOW_UPDATE環境変数を使います。これらの質問は初回インストール時だけで、既存導入への更新実行時は尋ねません。

スクリプトを確認してから実行する場合:

curl -fsSLO \
  https://raw.githubusercontent.com/scolor-dev/deckox/main/packaging/scripts/install.sh
less install.sh
sudo sh install.sh

特定バージョンを選ぶ場合:

curl -fsSL \
  https://raw.githubusercontent.com/scolor-dev/deckox/main/packaging/scripts/install.sh \
  | sudo DECKOX_VERSION=v0.6.8 sh

ダウンロードや変更を行わずに予定を確認する場合:

sh install.sh --dry-run
sh install.sh --version

管理対象ファイルだけを削除する場合:

sudo sh install.sh --uninstall

アンインストール後も/etc/deckox、/var/lib/deckox、バックアップ、deckoxユーザーとグループは保持されます。すべて消す場合は、後述の「完全削除」を参照してください。

ローカル配布物を検証する場合は、アーカイブと同じ場所に.sha256ファイルを置いて指定します。

sudo DECKOX_ARCHIVE=/tmp/deckox-aarch64-unknown-linux-musl.tar.gz \
  sh install.sh

インストーラーが行う処理

1. 前提確認
root権限と必要なLinuxコマンドの存在を確認
2. CPU判定
uname -mからx86-64またはARM64を選択
3. 検証
アーカイブとSHA-256を照合し、配布物内のVERSIONと指定バージョンを比較。不完全な既存導入や未確認ユニットは変更前に拒否
4. ユーザー
deckoxグループとシステムユーザーを未作成の場合のみ作成
5. 初期設定
初回導入時だけ、対話端末が使える場合に「待受アドレス(ローカルのみ/LAN内のこのホストのアドレス)」「ホスト再起動をUIから許可するか」「更新の適用をUIから許可するか」を尋ねる。既存導入(更新実行)では一切尋ねず既存の選択を維持。DECKOX_LISTEN_ADDR・DECKOX_ALLOW_REBOOT・DECKOX_ALLOW_UPDATE環境変数で無人インストール時にも指定可能
6. 配置
更新前の管理対象ファイルを/var/lib/deckox/backupsへ保存し、2バイナリ、Vue成果物、版情報、systemdユニットを配置。既存設定は維持
7. 認証
初回だけ管理者パスワードを生成し、Argon2idハッシュを/var/lib/deckoxへ配置。旧配置からの更新時は既存値を移行して維持
8. 起動
deckox-agentとdeckox-serverをenableして起動確認。失敗時は管理対象ファイルを更新前へ戻して旧サービスを再起動

導入後の確認

systemctl status deckox-server deckox-agent
journalctl -u deckox-server -u deckox-agent -f

初回インストール時は管理者パスワードがターミナルへ一度だけ表示されます。更新時は既存のパスワードが維持されます。

管理画面の「設定」では、GitHubの最新安定版を手動確認できます。新しい版がある場合はReleaseページと、対象タグを固定した更新コマンドを表示します。allow_updateを許可していない既定状態では、Deckox自身がroot権限で自動更新することはありません。

ログイン後は管理画面の「診断」で、Server・Agentの接続、ホスト情報、Deckoxのsystemdユニット状態をまとめて確認できます。問題を共有するときは、画面から安全な固定項目だけを含むJSONレポートを保存できます。Agentが停止していてもServer側の部分診断は表示されます。

管理画面の「監査ログ」では、ログイン・パスワード変更・TOTP設定変更・サービス操作・ホスト再起動・SSHコンソールからのCLI操作を時系列で確認でき、イベント種別・結果での絞り込みとJSON保存に対応します。

管理者パスワードを変更する

通常は管理画面の「設定」から、現在のパスワードと12文字以上の新しいパスワードを入力します。現在のパスワード確認に5分間で5回失敗すると一時的に制限されます。変更後は全セッションが失効し、完了案内が表示されたログイン画面から新しいパスワードで再ログインします。

設定画面でTOTPによる二要素認証を有効にしている場合は、パスワード確認後にコード入力を求める2段階ログインになります。無効化・有効化の操作は「設定」画面のTOTPセクションから行います。

ログインできない場合の復旧

管理画面へ入れない場合は、SSH接続したコンソールからreset-passwordサブコマンドでパスワードだけを再設定できます。TOTPの設定は変更されません。rootで実行してください。Agentが自分で持つパスワード確認用のハッシュ(/etc/deckox/admin-verifier、root専用)も同時に更新されます。

printf '%s' '新しいパスワード' | sudo deckox-server reset-password
sudo systemctl restart deckox-server

TOTPの認証アプリとリカバリーコードを両方失った場合は、disable-totpで二要素認証だけを無効化できます。

sudo -u deckox deckox-server disable-totp
sudo systemctl restart deckox-server

どちらの操作も監査ログ(管理画面の「監査ログ」またはGET /api/v1/audit)に記録されます。

初回インストール時に対話でLAN内のアドレスを選んでいれば、既にそのアドレスで待ち受けています。既定(ローカルのみ)のままの場合、別端末から一時的に確認するにはssh -L 8080:127.0.0.1:8080 user@serverでトンネルを作成します。

LAN内の端末から常時アクセスする

初回インストール時に対話プロンプトで「LAN内のこのホストのアドレス」を選ぶか、非対話インストールならDECKOX_LISTEN_ADDR=192.168.1.21:8080のように環境変数を指定すると、この設定込みで導入されます。既にインストール済みのホストで後から変更したい場合は、サーバーのLANアドレスを確認し、そのアドレスだけへsystemdの待受設定を上書きします。次の例では192.168.1.21を使用します。

sudo systemctl edit deckox-server
[Service]
Environment=DECKOX_LISTEN_ADDR=192.168.1.21:8080
sudo systemctl restart deckox-server

同じLANのMacやWindows PCからhttp://192.168.1.21:8080/を開きます。DHCPを利用している場合は、ルーター側でサーバーのアドレスを予約してください。

外部公開禁止: 管理者認証は実装済みですがTLS終端はありません。HTTPSリバースプロキシなどを用意するまで待受アドレスを外部向けに変更しないでください。

操作を許可するサービス

ホスト再起動を許可する

ホスト再起動は初期状態で無効です。初回インストール時の対話プロンプトで許可するか選べます(非対話インストールならDECKOX_ALLOW_REBOOT=true環境変数)。既にインストール済みのホストで後から変更したい場合は、/etc/deckox/agent.tomlへ次を設定します。

[system]
allow_reboot = true

設定画面から実行するときは管理者パスワードの再確認が必要です。要求後は管理画面が新しいServerプロセスを検知し、復帰するとログイン画面へ戻ります。設定変更後はAgentを再起動します。

sudo systemctl restart deckox-agent

管理画面からの更新の適用を許可する

管理画面から更新を実行する機能も初期状態で無効です。初回インストール時の対話プロンプトで許可するか選べます(非対話インストールならDECKOX_ALLOW_UPDATE=true環境変数)。既にインストール済みのホストで後から変更したい場合は、/etc/deckox/agent.tomlへ次を設定します。

[system]
allow_update = true

有効化すると、更新確認で新しい版が見つかっている間だけ設定画面に「今すぐ更新」が表示されます。実行時は管理者パスワードの再確認が必要です。確認後、Serverが確認済みバージョンのinstall.shをGitHubから取得してAgentへ渡し、Agentは通常のインストーラーと同じバックアップ・起動確認・失敗時ロールバックの手順を、Agent自身の再起動に巻き込まれない独立したsystemdユニットとして実行します。設定変更後はAgentを再起動します。

sudo systemctl restart deckox-agent

systemdサービス操作を許可する

/etc/deckox/agent.tomlへ、起動・停止・再起動・有効化・無効化とjournalログ閲覧を許可するsystemdサービスを完全一致で指定します。初期値は空で、変更操作とログ閲覧はすべて拒否されます。

[services]
allowed = [
  "nginx.service",
  "postgresql.service",
]

変更後はAgentを再起動します。

sudo systemctl restart deckox-agent

初回のみ再起動が必要ですが、その後は管理画面のサービス一覧から許可リストへの追加・削除を直接行えます。追加時はサービスの実在を確認し、削除時は確認ダイアログを挟みます。deckox-agent.service・deckox-server.service自身は許可リストへ追加できません。

管理画面では許可したサービスのjournalログを最大500行まで表示し、全件・エラー・警告・情報で絞り込め、表示中の内容をJSONファイルとして保存できます。任意のjournalctl引数は提供せず、対話操作は通常のSSHを利用します。

ソフトウェアのインストール・削除・更新を許可する

固定のカタログはありません。自分でインストールしたソフトウェアは、既定(auto_adopt = true)で自動的に管理対象になります。apt では、依存・推奨で束ねられるもの(docker-ceに対するdocker-ce-cliなど)は親の下にまとめて表示します。それ以外は、管理画面の「ソフトウェア」画面で「このホストにインストール済み」から選ぶか、パッケージ名を入力して追加します。名前は、そのホストに既に設定済みのリポジトリか、インストール済みのパッケージの中で実在確認したうえで/etc/deckox/agent.tomlの[software]許可リストへ追加されます。管理から外したものはdismissedに記録され、自動では戻りません。自動追加を止めるにはauto_adopt = falseにします。第三者リポジトリやGPG鍵を新たに追加することはありません。管理対象でないソフトウェアは、状態の閲覧はできますが変更操作はすべて拒否されます。

[software]
allowed = [
  "docker.io",
  "git",
]

手動で編集した場合はAgentを再起動します。

sudo systemctl restart deckox-agent

通常は管理画面の「ソフトウェア」画面からパッケージ名を入力するだけで許可リストへの追加・削除が行え、Agentの再起動は不要です。インストール・削除・更新の実行には管理者パスワードの再確認が必要です。

apt(Debian・Ubuntu・Raspberry Pi OSなど)・dnf(Fedora・RHEL・Rocky Linux・AlmaLinuxなど)・pacman(Arch Linuxなど)・zypper(openSUSEなど)に対応し、Agent起動時にホストのパッケージマネージャーを自動判定します。pacmanホストではインストール・更新のたびにホスト全体のパッケージも同時に最新化されます。Alpine Linuxには未対応です。

Webhook通知を有効にする

管理画面を開いていなくても異常に気づけるよう、Webhook URLを設定すると許可済みサービスの障害・Swap使用率・ディスク使用率・Agentへの接続断・新しいDeckoxバージョンの公開をServerが自動で監視し通知します。初期状態では無効です。

sudo systemctl edit deckox-server
[Service]
Environment=DECKOX_WEBHOOK_URL=https://example.com/webhook
sudo systemctl restart deckox-server

設定後は30秒間隔で状態を確認し、変化した瞬間(発生時・復旧時)だけ{"event", "message", "text", "timestamp_ms"}を含むJSONをPOSTします。Slack等のシンプルな受信Webhookはtextフィールドをそのまま表示に使えます。送信結果は監査ログにも記録されます。設定画面には設定状況が表示され、「テスト通知を送信」ボタンで実際に届くか即座に確認できます。

v0.3.2からの更新

v0.3.3ではWebコンソールを削除しました。更新時は旧deckox-terminal.serviceをDeckox管理のユニットだと確認してから停止・無効化し、ユニットとバイナリを削除します。

旧アカウントのホーム・nologinシェル・主グループがDeckoxの作成条件と一致する場合だけ、deckox-terminalユーザーとグループを削除します。/var/lib/deckox-terminalが空でなければデータ保護のため残し、インストーラーへ警告を表示します。

危険な操作のパスワード確認(Agentによる検証)

ソフトウェアの操作、ホストの再起動、セルフアップデートは、管理者パスワードの再入力が必要です。Serverが確認するのに加えて、Agentも自分でパスワードを検証します。Serverが乗っ取られても、管理者がその場でパスワードを入力しない限り、これらの操作をAgent経由で実行できません。

  • Agentは、root専用のファイル/etc/deckox/admin-verifierにパスワードのハッシュを持ちます。Serverのユーザー(deckox)は書き換えられません。
  • 初回(既存環境の更新時を含む)は、Serverのアカウントファイルから、Agentが起動時に一度だけ作成します。
  • 管理画面でパスワードを変えると、Serverは先にAgentへ通知します(Agentが古いパスワードを検証してから、新しいハッシュを保存します)。Agentが止まっているときは、パスワードは変更されません。
  • reset-passwordは、rootで実行すると、Agentの確認用ハッシュも更新します。deckoxユーザーで実行した場合は、Agentの更新はできないと警告し、それまで確認が必要な操作は拒否されます(安全側に倒れます)。
  • 間違ったパスワードが5回続くと、Agentは5分間、確認を受け付けません。

確認を求める操作は、agent.tomlの[security] confirmで追加できます。初期値は、現在の画面が既にパスワードを求めるもの(software_action、system_reboot、system_update)です。ほかにservice_allowlist、software_allowlist、service_stop、schedule_changeを指定できます(画面がパスワード入力に対応するまでは、指定しないでください)。

[security]
confirm = ["software_action", "system_reboot", "system_update"]

sudo -u deckox deckox-server doctorのagent passwordの行で、Agentが確認用のハッシュを持っているかを確認できます。

使わない機能を止める(モジュール)

Agentの機能は、モジュール単位で無効にできます。初期状態では、すべて有効です。/etc/deckox/agent.tomlの[modules]に、止めたいモジュールを書いて、Agentを再起動します。

[modules]
disabled = ["software", "power"]
モジュール内容
systemシステム情報とメトリクス
powerホストの再起動
update管理画面からのセルフアップデート
storageマウントとディスクの一覧
diagnostics診断
backups更新前バックアップの一覧
servicesサービスの一覧・操作・ログ
schedulesサービスの定期実行(servicesが必要)
softwareソフトウェアの管理

Server側の機能も、同じように止められます。Serverのユニット(/etc/systemd/system/deckox-server.service)のEnvironment=DECKOX_DISABLED_MODULES=に、カンマ区切りで書いて、Serverを再起動します(書き間違いは、理由を表示して起動を拒否します)。

Serverのモジュール内容
audit監査ログの画面とダウンロード(記録そのものは止まりません)
realtimeメトリクスのリアルタイム配信
notificationsWebhookの通知とテスト送信(監視の常駐処理も止まります)
update-checkGitHubの最新版の確認
 
Environment=DECKOX_DISABLED_MODULES=audit,realtime

止めたモジュールの経路は404を返し、そのモジュールだけが使う常駐処理は起動しません。書き間違いや、依存先(例: schedulesに対するservices)だけを止める設定は、Agentが理由を表示して起動を拒否します。状態はsudo -u deckox deckox-server doctorのagent.tomlの行で確認できます。

状態の確認(診断コマンド)

Web画面に入れないときは、SSHから1コマンドで状態を確認できます。

sudo -u deckox deckox-server doctor
sudo -u deckox deckox-server totp-status

doctorは、次の項目を [ OK ]・[WARN]・[FAIL] で1行ずつ表示します。[FAIL]があると終了コードが2になります。

項目確認内容
version実行中のバイナリと、インストールされた版情報が一致するか(更新が途中で止まった、または再起動していないと警告)
agent unit / server unitsystemdユニットがactiveか
agentAgentのUnixソケットに接続でき、ホスト情報を返すか
agent.tomlTOMLとして読めるか(構文エラーだとAgentは起動しません)。[system]・[software]・[services]が揃っているか。再起動・更新の許可、許可サービス数、管理パッケージ数、自動追加の状態
web filesWeb画面のファイル(index.html)があるか
account管理者アカウントを読めるか。二段階認証の有効・無効と、残りのリカバリーコード数

totp-statusは、二段階認証が有効か、リカバリーコードがあと何個かだけを表示します(読み取り専用)。/etc/deckox/agent.tomlを読むため、deckoxユーザー(またはroot)で実行してください。

前の版へ戻す

更新でおかしくなったときは、前の版を指定して入れ直すのが最も簡単です。設定とデータは保持されます。

curl -fsSL https://raw.githubusercontent.com/scolor-dev/deckox/main/packaging/scripts/install.sh \
  | sudo DECKOX_VERSION=v0.6.6 sh

ネットワークに繋がらないなど、ダウンロードできないときは、更新のたびに保存される更新前バックアップから戻します。

ls /var/lib/deckox/backups/          # 例: 20260919T120000Z-0.6.6(日時-更新前の版)
B=/var/lib/deckox/backups/20260919T120000Z-0.6.6

sudo systemctl stop deckox-server deckox-agent
sudo cp -p $B/deckox-agent $B/deckox-server /usr/local/bin/
sudo cp -p $B/deckox-agent.service $B/deckox-server.service /etc/systemd/system/
sudo cp -p $B/VERSION /usr/local/share/deckox/VERSION
sudo rm -rf /usr/local/share/deckox/web
sudo cp -R $B/web /usr/local/share/deckox/web
sudo systemctl daemon-reload
sudo systemctl start deckox-agent deckox-server
sudo -u deckox deckox-server doctor

バックアップに含まれるのは、バイナリ2つ、systemdユニット、Web画面、版情報です。設定(/etc/deckox)とデータ(/var/lib/deckox)は、更新でも書き換えずに保持されるため、戻す対象に含まれません。設定の巻き戻しは「設定のバックアップと復旧」を参照してください。

設定のバックアップと復旧

Agentは、管理画面の操作で/etc/deckox/agent.tomlを書き換えるたびに、直前の内容をagent.toml.bak.1(最新)からagent.toml.bak.3まで、3世代保存します。

ls -l /etc/deckox/

設定がおかしくなったら、直前の状態へ戻します。

sudo cp -p /etc/deckox/agent.toml.bak.1 /etc/deckox/agent.toml
sudo systemctl restart deckox-agent

手で編集する前は、自分でもバックアップを取ります。編集後は、構文を確認してから再起動してください(Python 3.11以降)。

sudo cp -p /etc/deckox/agent.toml /etc/deckox/agent.toml.manual.bak
sudoedit /etc/deckox/agent.toml
sudo python3 -c "import tomllib; tomllib.load(open('/etc/deckox/agent.toml','rb')); print('OK')"
sudo systemctl restart deckox-agent

バックアップも失われた場合は、標準の設定を作り直します。許可していたサービスやソフトウェアは、必要に応じて足してください。

sudo tee /etc/deckox/agent.toml >/dev/null <<'EOF'
socket = "/run/deckox/agent.sock"

[system]
allow_reboot = false
allow_update = false

[software]
auto_adopt = true
allowed = []
dismissed = []

[services]
allowed = []
EOF
sudo chown root:deckox /etc/deckox/agent.toml
sudo chmod 640 /etc/deckox/agent.toml
sudo systemctl restart deckox-agent
v0.6.6以前の注意: これらの版は、サービスやソフトウェアの許可・解除の書き込みで、[software]などの表が消えることがありました。v0.6.8以降へ更新してから復旧してください。

完全削除(データも含めてすべて消す)

--uninstallは、バイナリ・Web画面・systemdユニット・版情報だけを削除します。設定、管理者アカウント、監査ログ、スケジュール、更新前バックアップ、deckoxユーザーは残ります。これらまで消すには、アンインストールの後に次を実行します。

curl -fsSL https://raw.githubusercontent.com/scolor-dev/deckox/main/packaging/scripts/install.sh -o install.sh
sudo sh install.sh --uninstall

sudo rm -rf /etc/deckox /var/lib/deckox /run/deckox
sudo userdel deckox
getent group deckox >/dev/null && sudo groupdel deckox
場所内容
/etc/deckox設定(agent.toml、server.toml)とそのバックアップ
/var/lib/deckox管理者のパスワードハッシュと二段階認証、監査ログ(audit.log)、スケジュール(schedules.json)、更新前バックアップ(backups/)
/run/deckoxAgentのソケット(再起動で消える一時領域)
deckoxユーザーとグループServerの実行アカウント
元に戻せません: パスワード、二段階認証、監査ログ、バックアップも消えます。再インストールすると初期状態になり、管理者パスワードの設定から始まります。必要なものは、先に別の場所へコピーしてください。

systemdのログ(journalctl)はDeckoxの管理外です。消す場合はsudo journalctl --vacuum-time=1sを使います(ホスト全体のログが対象になります)。
